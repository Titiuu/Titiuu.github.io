早期的 Agent 工程形态主要依赖 **Function Call**。模型负责理解用户意图，并在需要时输出结构化参数，由外部程序执行对应函数。这种方式让大模型从“只会生成文本”扩展到“可以调用工具”，是 Agent 能力落地的起点。但在这个阶段，工具调用更多是由应用开发者自行约定，函数 schema、参数格式、调用链路和错误处理方式都比较分散。

随后，各家模型厂商陆续推出了内置的 **Tool Call / Tool Use** 能力。相比早期手写 Function Call，内置工具调用在模型侧有了更好的结构化输出支持，也提升了工具选择、参数生成和多轮调用的稳定性。但问题也随之出现：不同厂商的 tool call 格式、协议细节、消息结构、流式返回方式并不统一。应用一旦接入多个模型，就需要为不同模型分别适配工具协议，工具生态难以复用，也不利于跨模型、跨平台扩展。

为了解决工具接入不统一的问题，业界开始引入 **MCP（Model Context Protocol）** 这类标准化协议。MCP 的核心价值是把模型、工具和外部资源之间的连接方式标准化，使工具可以像插件一样被注册、发现和调用。它降低了工具接入成本，也让 Agent 能够更方便地连接文件系统、数据库、浏览器、代码仓库、企业内部 API 等外部能力。不过，MCP 的一个现实问题是：工具定义、资源描述、调用说明和上下文信息往往需要显式暴露给模型，当工具数量增多时，会占用大量上下文窗口，增加模型理解负担，也可能带来选择混乱和成本上升。

在这种背景下，**SKILL.md** 代表了一种更轻量、更面向任务组织的能力封装方式。它不再把所有工具细节一次性塞进上下文，而是把一个能力封装成可触发、可阅读、可执行的 Skill。模型先根据用户意图判断是否需要某个 Skill，只有在需要时才读取对应的 SKILL.md；如果还需要更细节的信息，再逐步读取参考文档、示例、脚本或工具说明。这就是所谓的 **三层渐进式披露**：第一层是简短的 Skill 描述，用于触发；第二层是 SKILL.md，说明任务流程、约束和关键方法；第三层才是更详细的 references、examples、scripts 等资源。

因此，从 Function Call 到 Tool Call，再到 MCP，再到 SKILL.md，可以看作 Agent 工程化的一条演进路径：早期关注“模型能不能调用函数”，后来关注“工具调用能不能标准化”，再后来关注“工具和知识如何在复杂任务中低成本、低上下文占用地组织起来”。MCP 更偏向工具连接协议，解决“外部能力如何接入”；SKILL.md 更偏向任务能力封装，解决“复杂能力如何被模型按需发现、理解和使用”。两者并不是互相替代关系，而是可以组合使用：MCP 提供底层工具连接，SKILL.md 提供上层任务编排和渐进式上下文管理。
