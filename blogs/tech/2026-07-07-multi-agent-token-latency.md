# 多 Agent 业务开发实践：如何减少 Token 消耗和等待时间

做多 agent 系统时，很多人会认为：只要把任务拆给更多 agent，系统就会更聪明、更快。

实际业务开发里经常相反。agent 数量变多以后，如果职责边界不清、上下文传递太随意、输出格式不可控，系统会很快变成另一种形态的低效工作流：

- 每个 agent 都带着一大段重复背景。
- 主 agent 把所有中间过程都塞进上下文。
- 子 agent 输出长篇自然语言，后续流程只能再让模型读一遍。
- 明明可以同时做的检索、分析、校验，被串行排队执行。

结果就是 token 消耗变高，端到端耗时变长，稳定性也变差。

所以多 agent 的优化重点，在于把每个 agent 变成一个边界清楚、输入输出可控、可以被调度的业务单元。我的体会可以总结成三个原则：**单一职责、并行调用、结构化输入输出**。

---

## 一、多 Agent 系统为什么容易浪费？

单 agent 系统的问题通常比较直观：上下文越来越长，工具结果越来越多，模型每一轮都要读更多历史。

多 agent 系统的问题更隐蔽，因为它看起来已经做了拆分。但如果拆分方式不对，反而会产生额外成本。

比如一个业务任务是“根据客户需求生成解决方案”。一个粗糙的多 agent 设计可能是：

```text
主 agent
  -> 需求分析 agent
  -> 行业研究 agent
  -> 方案撰写 agent
  -> 风险评估 agent
  -> 最终汇总
```

这个结构看起来合理，但真正跑起来以后，常见问题是：

- 每个 agent 都收到完整客户背景、完整历史对话和完整业务资料。
- 行业研究 agent 输出几千字调研报告，方案撰写 agent 又把它整篇读进去。
- 风险评估 agent 其实只需要方案中的关键承诺，却被喂了全部上下文。
- 主 agent 等一个子任务完成后，才开始下一个本来无依赖的子任务。

这时候，多 agent 并没有降低复杂度，只是把同一份复杂度复制到了多个地方。

真正有效的多 agent 设计，应该让每个子 agent 只看到它需要看的内容，只产出下游真正会用的结果，并且让没有依赖关系的链路尽量并行完成。

---

## 二、原则一：单一职责，降低单个 Agent 的上下文长度

第一个原则是：**agent 的职责要尽量单一**。

单一职责会直接影响 token 和耗时。一个 agent 的职责越泛，它需要读取的背景越多，需要携带的规则越多，也更容易在执行过程中调用不必要的工具。

比如“分析客户需求并生成方案”这个任务，如果交给一个通用 agent，它可能需要同时理解：

- 客户原始需求。
- 产品能力边界。
- 行业上下文。
- 竞品信息。
- 交付风险。
- 输出格式。
- 业务话术。

这些内容全部放进同一个上下文，模型每一轮都要重新消化。即使其中有些信息只在某个阶段有用，也会在后续推理里继续占 token。

更好的做法是按职责拆开：

```text
需求解析 agent：只负责从原始输入中抽取目标、约束和缺失信息
资料检索 agent：只负责找到和需求相关的资料片段
方案生成 agent：只负责基于结构化需求和资料摘要生成候选方案
风险校验 agent：只负责检查方案中的风险、冲突和不确定项
汇总 agent：只负责把已确认的信息整理成最终输出
```

这里每个 agent 的上下文都变短了。需求解析 agent 不需要看完整知识库，风险校验 agent 不需要读取原始长对话，汇总 agent 也不需要知道资料检索过程里失败过哪些查询。

单一职责还有一个额外收益：prompt 可以更短。一个通用 agent 往往需要很长的系统指令来描述所有行为，而单一职责 agent 的指令可以非常直接：

```text
你只负责从输入中抽取需求字段。
不要生成解决方案。
不要补充资料。
缺失字段标记为 null。
```

职责越窄，模型越不需要“猜自己现在该做什么”，输出也越稳定。

在业务系统里，我通常会用一个简单标准判断是否应该拆 agent：

> 如果某段逻辑只需要完整上下文中的一小部分信息，并且输出可以被下游明确消费，它就适合拆成独立 agent。

反过来，如果两个步骤强依赖同一段连续推理，中间结果也很难定义清楚，强行拆开反而会增加通信成本。

## 三、原则二：并行调用，减少业务链路等待时间

第二个原则是：**互不依赖的链路应该并行调用多个子 agent 完成**。

多 agent 系统降低耗时的主要机会，在于让多个等待过程彼此重叠。

很多业务流程天然有 fan-out 结构：

```text
用户输入
  -> 需求解析
  -> 同时执行：
       资料检索
       历史案例匹配
       合规风险检查
       竞品信息整理
  -> 汇总结果
  -> 生成最终方案
```

这些子任务之间并不一定互相依赖。资料检索不需要等历史案例匹配完成，合规风险检查也不一定需要等竞品信息整理完成。如果串行执行，端到端耗时就是所有步骤耗时相加；如果并行执行，总耗时更接近最慢的那条链路。

这对真实业务体验很重要。用户感知的是最终等待时间，而不是系统内部调用了多少次模型。

当然，并行不是无脑 fan-out。并行调用前需要先判断两件事：

1. 子任务是否真的没有依赖关系。
2. 子任务的输入是否已经足够明确。

比如“风险校验”如果依赖最终方案，那它就不能和方案生成并行。但“从客户需求中识别敏感行业限制”可以和资料检索并行，因为它只依赖原始需求。

一个比较稳的执行方式是先用一个轻量 agent 或代码逻辑做任务规划，把业务流程切成两类：

```text
必须串行：
需求解析 -> 方案生成 -> 最终汇总

可以并行：
资料检索
案例匹配
约束识别
风险线索收集
```

主 agent 或 orchestrator 只负责调度，不要亲自完成所有子任务。它发起并行任务后，等待结构化结果返回，再进入下一阶段。

这种设计的关键是：**并行任务返回的结果必须足够小、足够稳定**。如果每个子 agent 都返回一大篇自然语言报告，主 agent 汇总时仍然会被长上下文拖慢。

因此，还需要约束子 agent 之间的交接方式。

---

## 四、原则三：输入输出要小而结构化

第三个原则是：**每个 agent 都要定义好输入输出格式，最好是小的结构化 JSON，而不是纯文本长回复**。

在多 agent 系统里，agent 之间的输出主要是供下游流程消费的中间数据。既然是中间数据，就应该尽量稳定、紧凑、可解析。

比如需求解析 agent 的输出，不应该是：

```text
用户主要希望提升客服效率，同时要求部署成本低，并且最好能复用现有知识库。
他们似乎比较关注准确率，但没有明确说预算和上线时间。
```

更适合输出为：

```json
{
  "goal": "提升客服效率",
  "constraints": ["部署成本低", "复用现有知识库"],
  "preferences": ["准确率高"],
  "missing_fields": ["预算", "上线时间"]
}
```

这样做有三个直接收益。

第一，减少 token。JSON 字段通常比一大段解释性文字更短，下游也不需要再读取无关铺垫。

第二，流程可以用代码控制。比如 `missing_fields` 非空时，系统可以直接进入追问流程；`constraints` 里出现“本地部署”时，可以走私有化方案分支。这些判断不需要再让模型重新读一段文本后做分类。

第三，一致性更好。结构化输出天然适合校验、重试和降级。字段缺失、类型错误、枚举值不合法，都可以被 runtime 发现，而不是等到后续 agent 理解错了才暴露。

一个简单的 agent I/O 设计可以长这样：

```text
输入：
{
  "request": "客户原始需求",
  "known_context": {
    "industry": "教育",
    "company_size": "500-1000人"
  }
}

输出：
{
  "task_status": "ok",
  "summary": "一句话摘要",
  "facts": ["已确认事实"],
  "risks": ["风险项"],
  "next_action": "generate_plan"
}
```

这里不追求复杂 schema，重点是“小而够用”。字段越多，agent 越容易填错；字段越自由，下游越难控制。业务开发里更实用的做法是只保留下游真的会用的字段。

还要注意，结构化并不要求把所有内容都塞进 JSON。长文本可以放在独立字段里，但要控制边界：

```json
{
  "decision": "need_more_info",
  "missing_fields": ["预算", "上线时间"],
  "message_to_user": "为了给出更准确的方案，还需要确认预算范围和期望上线时间。"
}
```

代码读 `decision` 和 `missing_fields` 控制流程，用户只看到 `message_to_user`。这比让模型输出一整段自然语言，再从里面解析意图要可靠得多。

## 五、把三个原则组合到业务流程里

这三个原则最好一起使用。

只做单一职责，但输出仍然是长文本，主 agent 汇总时还是会消耗大量 token。

只做并行调用，但每个子 agent 都带完整上下文，整体成本会快速上涨。

只做 JSON 输出，但 agent 职责太宽，结构化结果也会变得臃肿和不稳定。

一个更合理的业务流程可以是：

```text
1. 需求解析 agent
   输入：用户原始需求
   输出：目标、约束、缺失字段

2. orchestrator 判断是否需要追问
   如果缺失关键字段，直接生成追问
   如果信息足够，进入下一步

3. 并行启动多个子 agent
   资料检索 agent：返回相关资料摘要和来源 id
   案例匹配 agent：返回相似案例 id 和匹配理由
   风险线索 agent：返回潜在风险标签

4. 方案生成 agent
   输入：结构化需求 + 资料摘要 + 案例摘要
   输出：候选方案、适用条件、关键假设

5. 风险校验 agent
   输入：候选方案 + 风险标签
   输出：通过项、风险项、修改建议

6. 汇总 agent 或代码模板
   输入：最终结构化结果
   输出：面向用户的完整回复
```

这里每一步都有明确边界：

- 子 agent 不共享完整历史，只接收自己需要的输入。
- 并行链路只依赖需求解析结果。
- 中间输出尽量是小 JSON。
- 主流程用代码判断状态和路由，模型只处理需要语义推理的部分。

这样的系统通常会更快，也更容易调试。因为当结果不符合预期时，可以直接看是哪一个 agent 的输入不足、输出字段错误，还是 orchestrator 的路由规则有问题。

---

## 六、结语

多 agent 系统的价值来自合理拆分：把复杂业务流程拆成可组合、可验证、可调度的推理单元，而不只是把一次大模型调用换成很多次小调用。

减少 token 消耗和耗时，本质上是三个工程动作：

- 用单一职责减少每个 agent 的上下文。
- 用并行调用减少端到端等待。
- 用小的结构化输入输出减少通信成本，并把流程控制交给代码。

agent 的边界清楚以后，上下文成本、链路耗时和错误位置都更容易判断，这样的多 agent 系统也更容易调试和维护。
