# ArkTS 动静态迁移：静态分析兜底 + AI Agent 修复的混合架构

鸿蒙 ArkTS 是一个以 TypeScript 为底、专为方舟运行时定制的静态强类型语言。它禁用了 `any`、`unknown`、解构赋值、`for...in`、运行时动态属性增删等大量 TypeScript 动态特性，强制所有类型在编译期完全确定，以便编译器生成高效方舟字节码做 AOT 优化。

从动态 TS/JS 代码迁移到静态 ArkTS，语法差异大、人工迁移成本高。我们设计了一套"**静态分析兜底 + AI Agent 修复**"的混合迁移工具：静态工具自动消除 95% 的语法差异，AI Agent 处理剩余 5% 的疑难杂症。目前该工具已覆盖 200+ 文件用例看护。

---

## 一、核心工作流：两阶段管道

整个迁移流程分为预处理与 Agent 闭环修复两个阶段。

### 1.1 阶段一：静态分析与初始化（覆盖 95% 差异）

```
源代码（.ts / .js / .ets）
    ↓
静态程序分析及修改工具
    ↓
自动修复 95% 动静态语法差异
    ↓
生成差异报告（行号、列号、违规规则）
    ↓
作为初始上下文输入给 Agent
```

第一阶段的核心是一套基于 AST 的静态分析与自动修改工具。它处理的是规则明确的、可批量替换的语法转换——比如 `var` → `let`、`<Type>value` → `value as Type`、`for...in` → `for` 循环等。这些规则的修复方案是确定性的，不需要 AI 参与，直接批量改。

输出产物是一份结构化差异报告，包含每条违规的精确位置（文件路径、行号、列号）和规则名（如 `arkts-not-support-any`）。

### 1.2 阶段二：Agent 推理与修复闭环（ReAct Loop）

剩余的 5% 是静态工具搞不定的——比如 `any` 类型需要根据上下文推断具体类型、复杂的接口重构需要理解业务语义。这交给 AI Agent 做闭环修复：

```
┌─────────────────────────────────────────────┐
│              Agent ReAct Loop                │
│                                              │
│  ① 推理 → ② 修改代码 → ③ 编译验证            │
│       ↓                            ↓         │
│  ④ 错误观察 ← ← ← ← ← ← ← ← ← ← ←┘         │
│       ↓                                      │
│  ⑤ 知识召回（双路径）                          │
│       ↓                                      │
│  ⑥ 上下文增强 → 回到 ①                        │
│                                              │
│  终止条件：编译通过 / 达到最大重试 / 死循环检测  │
└─────────────────────────────────────────────┘
```

#### 编译验证与错误观察

Agent 修改代码后立即调用编译器工具做编译验证。如果编译失败，捕获完整的编译器报错信息作为下一轮推理的输入。这相当于给 Agent 一个即时的"老师"——不需要人去告诉它改错了，编译器直接给出错误位置和原因。

#### 知识召回：双路径检索

当编译器报错时，Agent 需要知道"这个错误该怎么修"。我们设计了双路径检索：

**路径 A——语义检索（向量数据库）**

编译器报错信息作为 query，从本地向量数据库中检索最相关的文档块。底层是一份 520 页的 ArkTS 语法规范 PDF，按二级标题做 Chunk 切分，每个 Chunk 保留其所属章节的元信息。检索返回 Top 2 相关文档块。

**路径 B——精准检索（HashMap）**

静态扫描报告中的规则名（如 `arkts-not-support-any`）作为 key，从内存 HashMap 中 O(1) 查表，返回对应迁移指南的 JSON 项。这条路径的结果是绝对准确的——因为规则名和修复指南是一一映射的，不存在语义歧义。

```
编译器报错："arkts-not-support-any at line 42"
    │
    ├── 路径 A：嵌入向量 → 向量库搜索 → Top 2 规范 Chunk（语义相关）
    │
    └── 路径 B：规则名 HashMap 查表 → 迁移指南 JSON（绝对准确）
```

双路径互补：路径 B 解决的是"这个规则是什么意思"的问题（精准但覆盖面有限），路径 A 解决的是"这个错误上下文相关的规范细节"（覆盖面广但可能有噪音）。

#### 上下文窗口管理

Agent 在 ReAct 循环中会持续累积上下文——静态报告、编译报错、检索结果、历史修改记录。当上下文接近模型窗口限制时：

1. **优先摘要**：调用 Sub-agent 对过往轮次信息做摘要，保留关键事实
2. **遗忘机制**：如果摘要后仍超限，按 FIFO 策略丢弃最早轮次的编译报错和静态报告信息——这些信息在后期轮次中的边际价值递减

这套机制的思路是：**长上下文不是无限塞，而是分层压缩**。最新的编译报错永远保留（最相关），最早的历史信息优先丢弃（已过时）。

#### 死循环检测

记录每轮生成的修复 Patch。当检测到 Agent 多次尝试相同或高度相似的 Patch 时，强制终止循环，避免无效 Token 消耗。这本质上是一个 Patch 去重器——同样的修改方案试了三遍还不过，再试也不会过。

## 二、评估体系

单纯的"编译通过"不足以衡量迁移质量。我们建立了三层评估：

| 层级 | 指标 | 说明 |
|------|------|------|
| 基础 | 编译通过率 | 修改后的代码能否通过 ArkTS 编译器 |
| 语义 | 语义相似度 | 用大模型对修改前后代码做语义相似度打分，确保含义不变 |
| 回归 | 用例看护 | 基于 200+ 文件测试集做回归验证 |

语义相似度打分尤其关键。静态工具可以把 `any` 改成 `Object`——编译能过，但语义损失严重。LLM 评分能捕获这种"技术正确但语义退化"的情况。

## 三、演进路线图：从 Demo 到生产级工具

当前工具解决了单文件迁移的核心链路。以下六个维度的演进方向覆盖了从"能用"到"好用"的差距。

### 3.1 规模演进：从文件级到工程级

当前工具主要关注单文件语法检查。工程级迁移需要处理跨文件依赖、三方库编译链接、UI 转换逻辑：

- 接入整体编译构建流程日志，包含三方代码编译链接信息
- 支持 ArkUI 组件语法（如 `@State`、`@Prop` 装饰器）的迁移
- 基于工程构建日志反馈做全局检查——一个文件的修改可能导致另一个文件的编译错误

### 3.2 稳定性增强：工具调用与循环控制

静态分析工具和编译器作为 Agent 的外部工具，存在调用失败的可能性（传参错误、工具崩溃）。需要：

- **工具鲁棒性**：捕获工具调用失败，设计反思与重试机制。工具错误码和信息必须使能 LLM 进行故障排查——不能只抛一个 `exit code 1`
- **死循环检测**：已在当前版本实现 Patch 去重，后续需要更精细的语义级去重（两个 Patch 看似不同，实际修改了相同的逻辑）

### 3.3 可观测性：Token 与链路监控

缺乏细粒度监控是当前最痛的工程债务。需要建立 Token 消耗链路观测体系，回答三个问题：

- 经典的修复链路（如 `any 替换 → 联合类型`）每次消耗多少 Token？
- 高 Token 消耗的根本原因是检索回太多无关文档，还是推理轮次过多？
- 不同项目、不同代码特征的迁移成本差异在哪里？

### 3.4 质量体系：RAG 召回率评估

向量检索路径（路径 A）的召回效果目前缺乏量化评估。需要构建专门的用例看护集，评估向量召回的准确率与召回率，迭代优化 Chunk 切分策略和检索算法。520 页规范 PDF 的 Chunk 策略（窗口大小、重叠量、是否按二级标题切分）直接影响修复质量。

### 3.5 人机协作：Human-in-the-Loop

当 Agent 置信度低或多次重试失败时，不应强行给出一个"可能正确"的结果。设计思路是：

- 生成多个可选 Patch 方案（绕过不同约束条件的替代实现）
- 交由人类专家选择最佳方案
- 将人类选择作为反馈信号用于后续模型优化（RLHF 的天然数据源）

### 3.6 技术栈选型考量

当前工具的技术选型中几个值得记录的决策点：

**为什么用 HashMap 做路径 B 而不是全走向量检索？** 规则名到修复指南是一一映射的确定性关系，用向量检索反而引入语义歧义风险。`arkts-not-support-any` 的修复指南是唯一的，不需要"模糊匹配"。

**为什么用 Sub-agent 做摘要而不是直接截断？** 直接截断可能丢失关键的编译器错误行号和违规规则名——这些是精确信息，不能丢。Sub-agent 摘要可以保留关键事实（"第 3 轮修改了 X 文件的 Y 行，编译报错 Z"）而去掉冗余的完整代码块。

**为什么编译验证放在 Agent 循环内部而不是外部？** Agent 需要编译器的即时反馈来调整下一步推理。如果编译验证在 Agent 循环外部（比如 CI 里），Agent 就失去了最直接的纠错信号，退化成了"盲改"。

## 四、总结：混合架构的设计取舍

这个工具的核心设计选择是"静态分析覆盖 95%，AI Agent 覆盖 5%"。这个比例不是拍脑袋的——它反映了一个基本的工程判断：

- 95% 的语法差异是**规则的、可批量处理**的：`var` → `let`、尖括号类型断言 → `as`、`for...in` → `for` 循环。用 AI 处理这些是浪费 Token。
- 5% 的语法差异是**上下文的、需要语义理解**的：`any` 类型推断、接口重构、动态属性改静态声明。用规则处理这些几乎不可能。

这个架构的最大风险不是技术本身，而是比例的边界会随 ArkTS 语言演化而变动。今天的 95/5 可能随着 ArkTS 规范收紧变成 90/10 或 80/20。工具需要持续跟踪剩余差异的类型分布，在静态规则和 Agent 能力之间重新分配边界。
