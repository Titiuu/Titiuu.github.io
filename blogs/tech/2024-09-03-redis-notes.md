# Redis 面试笔记

这篇笔记整理 Redis 面试中最常见的问题：数据结构、线程模型、持久化、过期和淘汰、分布式锁、主从哨兵、Cluster，以及缓存场景题。写法偏复习向，先给结论，再补充版本差异和容易说错的点。

## 一、数据结构

### Redis 有哪些数据结构，有什么用

Redis 常用对象类型和底层编码大致如下。不同 Redis 版本的编码名称会变化，面试时要说明版本差异。

| 对象类型 | 常见编码 | 底层结构 | 典型用途 |
| --- | --- | --- | --- |
| String | int / embstr / raw | 整数或 SDS 动态字符串 | 缓存对象、计数器、分布式锁、session |
| List | ziplist / linkedlist / quicklist | 压缩列表、链表、quicklist | 简单队列、时间线 |
| Hash | ziplist/listpack / hashtable | 紧凑列表或字典 | 对象缓存、购物车 |
| Set | intset / hashtable | 整数集合或字典 | 去重、交并差、抽奖、共同关注 |
| ZSet | ziplist/listpack / skiplist | 紧凑列表或跳表 + 字典 | 排行榜、延迟队列、范围排序 |

Redis 后续还支持多种扩展结构：

- Bitmap：二值状态统计，例如签到、登录状态、活跃用户。
- HyperLogLog：海量基数统计，例如 UV，牺牲少量精度换空间。
- GEO：地理位置存储和附近位置查询。
- Stream：消息队列，支持消息 ID、消费组、ACK，比 List 更适合可靠队列场景。

### String 底层用什么结构

Redis String 底层主要使用 SDS，也就是 Simple Dynamic String。它相比 C 字符串增加了元数据：

- `len`：当前字符串长度，获取长度 O(1)。
- `alloc`：已分配容量，便于判断是否需要扩容。
- `flags`：编码类型，表示不同 SDS 头部格式。
- `buf`：真实字节数组。

SDS 的好处：

- O(1) 获取长度。
- 二进制安全，可以存储包含 `\0` 的数据。
- 扩容更安全，减少缓冲区溢出风险。
- 预分配和惰性释放策略减少频繁内存分配。

### ZSet 底层如何实现

ZSet 同时需要按 member 快速查分数，也需要按 score 有序范围查询。因此常见实现是：

- 字典：member -> score，支持 O(1) 查找 member。
- 跳表：按 score 和 member 排序，支持范围查询和排名操作。

当元素较少、元素较小时，早期 Redis 会使用 ziplist 紧凑存储。Redis 7.0 中 ziplist 已被 listpack 替代。常见阈值是元素数量小于 128 且元素长度小于 64 字节时使用紧凑结构，超过阈值后转为跳表结构；具体阈值可通过配置项调整。

### ziplist 和 listpack

ziplist 是一段连续内存组成的紧凑顺序结构，适合小数据量，节省内存。每个 entry 通常保存：

- 前一个节点长度。
- 当前节点编码类型。
- 当前节点数据。

ziplist 不支持高效随机访问，查找通常是 O(n)。它的典型问题是连锁更新：如果某个 entry 长度变化导致后一个 entry 的 prevlen 从 1 字节扩展到 5 字节，可能继续影响后续 entry。

listpack 的设计目标之一就是避免 ziplist 的连锁更新。它不在 entry 头部保存前一个节点长度，而是在 entry 尾部保存当前节点长度，反向遍历时从尾部解析，减少前面节点变化对后续节点的影响。

### 跳表是什么

跳表是一种多层有序链表。底层链表保存全部元素，上层链表保存部分元素作为索引。查找时从高层开始跳跃式定位，再逐层下降。

Redis 跳表节点层高通过随机算法决定：创建节点时生成随机数，如果小于某个概率阈值，例如 0.25，就增加一层，并继续尝试，直到随机数不满足条件或达到最大层数。这样整体能获得接近 O(log n) 的平均查找复杂度。

### 为什么 ZSet 用跳表不用 B+Tree

Redis 是内存数据库，不需要像磁盘数据库那样强依赖 B+Tree 的页结构来减少磁盘 IO。

跳表的优势：

- 实现简单，范围查询方便。
- 插入和删除只需要调整局部指针，不需要复杂的树旋转或页分裂。
- 按 score 范围遍历自然高效。
- 与 Redis 内存场景匹配，不需要为磁盘页访问优化。

不要说“跳表指针更少”。跳表每个节点可能有多层 forward 指针，空间不一定比树更少；更准确的是实现和范围操作更适合 Redis 的内存场景。

### Hash 如何扩容

Redis 字典使用两个哈希表 `ht[0]` 和 `ht[1]` 支持渐进式 rehash。

扩容流程：

1. 给 `ht[1]` 分配更大的空间。
2. 设置 rehash 索引，从 `ht[0]` 逐步迁移到 `ht[1]`。
3. 每次执行增删改查时顺带迁移一部分桶。
4. 迁移完成后释放 `ht[0]`，把 `ht[1]` 设为新的 `ht[0]`。

rehash 期间查询会同时查两个表。新增一般写入 `ht[1]`，避免继续扩大旧表。这样可以避免一次性迁移大字典导致 Redis 长时间阻塞。

## 二、线程模型

### Redis 为什么快

Redis 快的核心原因：

- 数据主要在内存中，访问延迟低。
- 核心命令执行是单线程，避免大量锁竞争和上下文切换。
- 使用 I/O 多路复用处理大量连接。
- 数据结构设计高效，针对常见操作做了优化。
- 协议简单，网络处理开销相对可控。

单线程并不代表 Redis 只能处理一个连接。Redis 通过 Reactor 模型监听多个 socket 事件，一个主线程处理连接、读取、命令执行和响应写回等核心流程。

### Redis 哪些地方用了多线程

Redis 的“单线程”通常指核心命令执行主流程单线程。实际 Redis 还有后台线程或子进程参与一些任务：

- 关闭文件。
- AOF fsync。
- 惰性释放大对象内存。
- RDB/AOF rewrite 通常由子进程完成。
- Redis 6.0 起支持网络 I/O 多线程，用于读写 socket 和协议解析辅助，但命令执行仍主要由主线程完成。

这个点面试容易被问：Redis 6 的 I/O 多线程不是让多个线程并发执行命令，而是分担网络读写开销。

### Redis 网络模型

Redis 经典模型是单 Reactor 单线程：

1. 主线程用 epoll/kqueue/select 等 I/O 多路复用机制监听事件。
2. 连接事件到来时 accept。
3. 可读事件到来时读取请求并解析。
4. 执行命令。
5. 可写事件到来时发送响应。

优点是模型简单、无锁、延迟稳定。缺点是单个慢命令、大 key 删除、大量网络读写都可能阻塞主线程。Redis 6.0 的 I/O 多线程主要缓解网络 I/O 压力，但慢命令和大 key 问题仍要避免。

### Redis 命令如何保证原子性

单条 Redis 命令在主线程中串行执行，因此天然具有原子性。

多个命令可以使用事务、Lua 脚本或函数保证一定程度的原子执行：

- `MULTI/EXEC`：按队列顺序执行，中间不会插入其他客户端命令，但不支持自动回滚。
- Lua 脚本：脚本整体原子执行，适合读改写组合逻辑。

## 三、持久化

### Redis 持久化方式

Redis 主要有 RDB 和 AOF 两种持久化方式，也可以混合使用。

RDB 是某个时刻的数据快照。Redis 通过 `SAVE` 或 `BGSAVE` 生成 RDB 文件，常见是后台子进程写快照。

优点：

- 文件紧凑，适合备份和全量恢复。
- 恢复速度通常较快。
- 对主进程影响较小。

缺点：

- 两次快照之间的数据可能丢失。
- fork 子进程和写快照会带来额外内存和 IO 压力。

AOF 是追加写命令日志。每次写命令执行后追加到 AOF 缓冲区，再按策略刷盘。

优点：

- 数据丢失更少，通常最多丢 1 秒。
- 日志可读性较好，便于分析和修复。

缺点：

- 文件可能比 RDB 大。
- 恢复需要重放命令，可能较慢。
- 需要 AOF rewrite 压缩日志。

### AOF 刷盘策略

常见 `appendfsync` 策略：

- `always`：每次写命令都 fsync，最安全，性能最差。
- `everysec`：每秒 fsync 一次，默认常用，性能和可靠性折中。
- `no`：交给操作系统决定刷盘，性能最好，丢数据风险更高。

AOF rewrite 会把当前数据状态重写成更紧凑的命令序列，避免 AOF 文件无限增长。

## 四、缓存淘汰和过期删除

### 缓存淘汰和过期删除的区别

过期删除处理的是设置了 TTL 的 key 到期后如何删除。

内存淘汰处理的是 Redis 内存达到 `maxmemory` 限制后，如何选择 key 淘汰以释放空间。

两者触发条件不同：过期删除看 key 是否到期，内存淘汰看内存是否达到限制。

### 过期删除策略

Redis 主要结合惰性删除和定期删除。

惰性删除：访问 key 时检查是否过期，过期就删除。

- 优点：节省 CPU。
- 缺点：冷数据如果一直不访问，可能长期占用内存。

定期删除：Redis 周期性随机抽取一部分带过期时间的 key 检查并删除。

- 优点：减少过期冷数据堆积。
- 缺点：扫描比例和频率需要折中，不能一次性全量扫描。

### 内存淘汰策略

常见策略：

- `noeviction`：不淘汰，写入报错。
- `allkeys-lru`：从所有 key 中按近似 LRU 淘汰。
- `volatile-lru`：从设置了过期时间的 key 中按近似 LRU 淘汰。
- `allkeys-lfu`：从所有 key 中按近似 LFU 淘汰。
- `volatile-lfu`：从设置了过期时间的 key 中按近似 LFU 淘汰。
- `allkeys-random`：从所有 key 中随机淘汰。
- `volatile-random`：从设置了过期时间的 key 中随机淘汰。
- `volatile-ttl`：优先淘汰剩余 TTL 更短的 key。

LRU 看最近访问时间，LFU 看访问频率。Redis 使用的是近似算法，不是严格全量排序。

## 五、分布式锁

### 分布式锁是什么

分布式锁用于在分布式系统中保护共享资源，保证同一时刻只有一个客户端执行关键逻辑。它本质上是跨进程、跨机器的互斥控制。

典型场景：

- 防止重复执行定时任务。
- 控制库存扣减。
- 避免缓存重建并发击穿。
- 分布式资源互斥访问。

### Redis 如何实现分布式锁

基础写法：

```text
SET lock_key unique_value NX PX 30000
```

含义：

- `NX`：key 不存在才设置成功。
- `PX`：设置过期时间，避免客户端宕机后锁永不释放。
- `unique_value`：标识锁归属，释放时必须校验。

释放锁要用 Lua 脚本保证“判断锁归属 + 删除 key”原子执行。

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### 为什么要设置过期时间

如果加锁后进程崩溃、网络中断或业务异常，锁可能无法主动释放。过期时间可以让锁最终自动释放，避免死锁。

关键点：设置锁值和过期时间必须是一个原子操作，不能先 `SETNX` 再单独 `EXPIRE`，否则中间宕机会留下无过期时间的锁。

### 锁过期了怎么办

如果业务执行时间超过锁 TTL，锁可能提前过期，其他客户端拿到锁，导致并发执行。

常见处理：

- 设置合理过期时间，大于业务最长执行时间。
- 业务逻辑幂等，避免重复执行造成错误。
- 使用 Redisson WatchDog 自动续期。Redisson 默认锁续期时间常见为 30 秒，后台看门狗会在持锁线程仍存活时续期。
- 对强一致要求极高的场景，考虑数据库锁、Zookeeper、etcd 等更合适的协调组件。

### 集群环境下分布式锁可靠性

单 Redis 主从复制是异步的。主节点加锁成功后如果还没同步到从节点就宕机，从节点被提升为主，锁可能丢失。

Redlock 试图通过多个独立 Redis 实例提高可靠性：客户端向多个实例加锁，超过半数成功且耗时在有效期内才认为加锁成功。

但 Redlock 对时钟、网络延迟和故障模型有争议。工程中要根据一致性要求选择方案：Redis 锁适合很多“尽力互斥 + 幂等兜底”的场景；强一致协调更适合 Zookeeper/etcd 或数据库事务方案。

## 六、集群与高可用

### 主从复制为什么有全量同步和增量同步

Redis 主从复制分为全量同步和增量同步。

全量同步常发生在：

- 从节点第一次连接主节点。
- 从节点复制偏移量太旧，主节点复制缓冲区找不到缺失数据。
- 主从复制 ID 不匹配。

全量同步通常由主节点生成 RDB 并发送给从节点，从节点加载 RDB 后再追增量命令。

增量同步依赖：

- 复制偏移量 offset。
- 复制积压缓冲区 `repl_backlog_buffer`。
- 主节点 replication id。

网络短暂断开后，如果从节点缺失的数据仍在 backlog 中，就可以增量补齐。为了降低全量同步概率，可以适当增大 `repl_backlog_size`。

### 主从复制能保证强一致吗

不能。Redis 主从复制通常是异步复制，属于更偏 AP 的设计，优先保证可用性和分区容忍，不能保证主从强一致。

从库读可能读到旧数据。对一致性要求高的读请求应走主库，或使用业务层版本校验、等待复制确认等策略。

### 哨兵机制

Sentinel 用于监控 Redis 主从并完成故障转移。

流程：

1. Sentinel 定期向主从节点发送心跳。
2. 单个 Sentinel 认为主节点不可达，标记主观下线。
3. 多数 Sentinel 都认为主节点不可达，标记客观下线。
4. Sentinel 之间选举 Leader。
5. Leader 从从节点中选择一个提升为新主。
6. 其他从节点改为复制新主。
7. 更新配置并通知客户端。

选择新主会考虑优先级、复制偏移量、运行 ID 等因素。更准确地说，不是简单选“ID 新”，而是优先选择优先级高、数据更完整、复制偏移量更靠前的从节点。

### Redis Cluster

Redis Cluster 用于分片和高可用。整个 key 空间分为 16384 个 hash slot，每个主节点负责一部分槽。

key 到槽的映射：

```text
slot = CRC16(key) % 16384
```

Cluster 优点：

- 横向扩展容量和吞吐。
- 支持节点故障转移。
- 客户端可以根据 MOVED/ASK 重定向访问正确节点。

缺点：

- 运维复杂度更高。
- 多 key 操作必须在同一槽位才方便执行。
- 扩缩容涉及槽迁移。
- 客户端需要支持 Cluster 协议。

## 七、场景题

### 为什么用 Redis

常见原因：

- 高性能读写，适合热点数据缓存。
- 支持丰富数据结构，能覆盖计数、排行榜、集合运算、队列等场景。
- 支持过期时间，适合缓存。
- 支持持久化、主从、哨兵、Cluster。
- 生态成熟，客户端和运维工具丰富。

### Redis 实现消息队列

常见方式：

- Pub/Sub：实时发布订阅，简单，但消息不持久，消费者离线可能丢消息。
- List：用 `LPUSH/BRPOP` 实现阻塞队列，简单，但缺少消息 ID、ACK、消费组。
- Stream：Redis 5.0 引入，支持消息 ID、消费组、ACK、pending list，更适合作为轻量消息队列。

如果是核心金融级消息系统，仍要优先考虑 Kafka、RabbitMQ、RocketMQ 等专业 MQ。

### 大 key 问题

大 key 指 value 很大或集合元素过多的 key，例如单个 String 超过 1MB，或者 Hash/List/Set/ZSet 包含大量元素。

问题：

- 占用内存大，迁移和复制成本高。
- 删除或过期可能阻塞主线程。
- 网络传输时间长。
- Cluster 下造成数据倾斜。

解决：

- 拆分大 key。
- 控制单个集合大小。
- 删除时使用 `UNLINK` 等异步释放方式。
- 对热大 key 做本地缓存或分片。
- 建立监控，定期扫描。

### 热 key 问题

热 key 是访问频率极高的 key，可能导致单 Redis 节点压力过大。

解决：

- 本地缓存热点数据。
- 热 key 拆分或复制到多个 key，读请求随机分散。
- Redis Cluster 分片。
- 读写分离，从节点承担读流量。
- 提前识别和预热热点数据。

### Redis 和 MySQL 如何保证一致性

缓存和数据库很难做到强一致，工程目标通常是最终一致。

常见 Cache Aside 模式：

读流程：

1. 先读缓存。
2. 缓存未命中读数据库。
3. 回写缓存。

写流程常用：

1. 更新数据库。
2. 删除缓存。

更推荐“先更新数据库，再删除缓存”。如果先删缓存再写数据库，中间有读请求可能把旧数据重新写入缓存。延迟双删是补救方案：先删缓存，写数据库，等待一小段时间后再删一次。

增强方案：

- 删除缓存失败时用消息队列或重试任务补偿。
- 使用 binlog 订阅异步删除或更新缓存。
- 给缓存设置合理 TTL。
- 业务上用版本号或更新时间防止旧值覆盖新值。

### 缓存雪崩、击穿、穿透

缓存雪崩：大量 key 同时过期或 Redis 故障，大量请求打到数据库。

解决：

- TTL 加随机抖动。
- 多级缓存。
- 限流降级。
- Redis 高可用。
- 热点数据预热。

缓存击穿：单个热 key 过期，大量请求同时打到数据库。

解决：

- 热 key 不设置过期或逻辑过期。
- 互斥锁，只允许一个请求回源重建缓存。
- 后台异步刷新。

缓存穿透：请求的数据缓存和数据库都不存在，导致每次都打到数据库。

解决：

- 缓存空值，并设置较短 TTL。
- 布隆过滤器提前判断 key 是否可能存在。
- 参数校验和限流。

布隆过滤器基于多个哈希函数和 bitmap，可以快速判断“一定不存在”或“可能存在”，存在误判但不会漏判。

### 秒杀场景怎么设计

可以从“分、缓、异、削、护、一致性”回答。

分：

- 集群部署和流量分片。
- 服务按领域拆分。
- 大 key 拆分。
- 分库分表。
- 读写分离。

缓：

- 多级缓存。
- Redis 缓存库存和活动信息。
- 热点数据预热。
- CDN 缓存静态资源。

异：

- 下单链路异步化。
- MQ 解耦扣库存、创建订单、支付超时关闭等流程。
- 事件驱动降低同步等待。

削：

- MQ 削峰填谷。
- 令牌桶、漏桶限流。
- 排队页或等待队列。

护：

- API Gateway 限流。
- 熔断、降级、隔离。
- 防刷和风控。
- 只保留关键链路。

一致性：

- Redis 预扣库存 + 数据库最终落库。
- 乐观锁或版本号防超卖。
- 分布式锁只用于小范围互斥，不应成为高并发主路径瓶颈。
- 幂等 ID 防重复下单。
- 失败补偿、对账任务、最终一致。
- 复杂分布式事务可考虑 TCC、Saga、事务消息等方案。

## 八、面试速答

- Redis 常见类型：String、List、Hash、Set、ZSet，扩展结构有 Bitmap、HyperLogLog、GEO、Stream。
- Redis String 底层是 SDS，支持 O(1) 获取长度和二进制安全。
- ZSet 大数据量下通常用跳表 + 字典，小数据量用 listpack。
- ziplist 有连锁更新问题，Redis 7.0 已用 listpack 替代。
- Redis 快主要因为内存、单线程命令执行、I/O 多路复用和高效数据结构。
- Redis 6.0 I/O 多线程只分担网络读写，命令执行仍主要单线程。
- RDB 是快照，AOF 是追加命令日志；二者可混合使用。
- 过期删除处理 TTL key，内存淘汰处理 maxmemory 压力。
- 分布式锁用 `SET key value NX PX`，释放锁用 Lua 校验 value 后删除。
- Redis 主从复制通常异步，不能保证强一致。
- Sentinel 负责故障转移，Cluster 用 16384 个槽做分片。
- 缓存一致性通常追求最终一致，常用更新 DB 后删除缓存。
- 雪崩是大量 key 同时失效，击穿是热 key 失效，穿透是查不存在的数据。
