# MySQL 面试笔记

这篇笔记整理 MySQL 面试中最常见的问题：范式、存储引擎、SQL 执行流程、InnoDB 存储结构、索引、事务、锁、日志和常见调优。写法偏复习向，先给直接结论，再补充面试里容易被追问的细节。

## 一、基础

### 数据库三大范式

第一范式要求字段具有原子性，每一列都是不可再拆分的基本数据项。比如把手机号列表塞进一个字段，就不符合 1NF。

第二范式建立在 1NF 上，要求非主属性完全依赖于主键，不能只依赖联合主键的一部分。它主要解决部分依赖问题。

第三范式建立在 2NF 上，要求非主属性不依赖于其他非主属性，也就是消除传递依赖。每个非主属性都应直接依赖主键。

范式的目标是减少数据冗余和更新异常。但工程中也会为了查询性能做适度反范式设计，例如冗余统计字段、宽表、缓存表。

### InnoDB 和 MyISAM 的区别

| 对比项 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | 支持事务 | 不支持事务 |
| 锁粒度 | 支持行锁，也有表级锁 | 主要是表锁 |
| 索引结构 | 聚簇索引，主键叶子节点存整行数据 | 非聚簇索引，索引和数据分离 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 依赖 redo log，恢复能力更强 | 恢复能力较弱 |
| 适用场景 | OLTP、事务、一致性要求高 | 读多写少、历史兼容场景 |

现在 MySQL 默认存储引擎通常是 InnoDB。除非有历史原因或特殊场景，面试和工程实践中基本围绕 InnoDB 展开。

### 一条 SELECT 语句的执行流程

一条 `SELECT` 大致会经过这些阶段：

1. 客户端和 MySQL Server 建立连接，完成认证和权限检查。
2. Server 层接收 SQL，进行词法、语法解析，生成解析树。
3. 预处理器检查表、字段是否存在，展开 `select *`，解析名字和权限。
4. 优化器生成执行计划，决定表连接顺序、是否使用索引、选择哪个索引。
5. 执行器根据执行计划调用存储引擎接口读取数据。
6. 存储引擎根据索引或全表扫描返回记录，执行器做过滤、排序、聚合等处理并返回结果。

查询缓存要按版本说明：MySQL 5.7 及以前存在 Query Cache，但因为失效成本高、并发性能差，MySQL 8.0 已移除。现代面试中不要把查询缓存当作默认流程重点。

索引下推 ICP 是优化器和存储引擎协作的一种优化：使用联合索引时，部分 `where` 条件可以在索引遍历阶段直接判断，减少回表次数。

## 二、InnoDB 数据存储

### MySQL 数据是如何存储的

以 InnoDB 为例，逻辑结构通常可以理解为：

```text
表空间 tablespace
  段 segment
    区 extent
      页 page
        行 row
```

页是 InnoDB 管理数据的基本单位，默认大小通常是 16KB。区由连续页组成，段按用途管理空间。

常见段：

- 数据段：存放聚簇索引叶子节点中的行数据。
- 索引段：存放索引页。
- 回滚段：存放 undo log，用于事务回滚和 MVCC。

### COMPACT 行格式

InnoDB 常见行格式包括 COMPACT、DYNAMIC 等。COMPACT 行格式大致包含：

- 变长字段长度列表：记录 `varchar` 等变长字段长度，通常逆序存储。
- NULL 值列表：用 bitmap 标识允许为 NULL 的列是否为 NULL。
- 记录头信息：记录删除标记、下一条记录位置、记录类型等。
- 隐藏列：`trx_id`、`roll_ptr`，必要时还有 `row_id`。
- 真实列数据。

隐藏列含义：

- `trx_id`：最近一次修改该行的事务 ID。
- `roll_ptr`：指向 undo log 版本链，用于回滚和 MVCC。
- `row_id`：如果表没有显式主键，也没有非空唯一索引，InnoDB 会生成隐藏 row_id。

MySQL 单行记录有大小限制，表定义层面一行最大约 65535 字节。对于 `TEXT`、`BLOB`、较长 `VARCHAR` 等大字段，InnoDB 可能把部分数据放到溢出页中，行内只保存前缀和指针信息。具体行为受行格式和字段长度影响。

## 三、索引

### 索引是什么，有什么好处

索引是帮助 MySQL 快速定位数据的数据结构。它的核心价值是减少扫描的数据量，让查找、排序、范围查询更高效。

代价也很明确：

- 占用额外存储空间。
- 插入、更新、删除时需要维护索引。
- 索引设计不合理会降低写入性能，也可能误导优化器。

### 索引分类

按数据结构：

- B+Tree 索引。
- Hash 索引。
- Full-text 全文索引。

按物理存储：

- 聚簇索引：InnoDB 主键索引，叶子节点存整行数据。
- 二级索引：辅助索引，叶子节点存主键值，需要回表获取完整行。

按字段特性：

- 主键索引。
- 唯一索引。
- 普通索引。
- 前缀索引。

按字段个数：

- 单列索引。
- 联合索引。

### 聚簇索引和非聚簇索引

InnoDB 的聚簇索引叶子节点存放整行数据。表数据本身就按聚簇索引组织，所以一张 InnoDB 表只能有一个聚簇索引，通常就是主键。

二级索引叶子节点存放索引列和主键值。通过二级索引查到主键后，再去聚簇索引查整行数据，这个过程叫回表。

MyISAM 的索引叶子节点通常存数据文件地址，数据和索引分开，因此属于非聚簇组织。

### B+Tree 的特点

MySQL InnoDB 常用 B+Tree 作为索引结构，原因包括：

- 非叶子节点只存 key 和指针，不存整行数据，单页能容纳更多 key，树高更低。
- 叶子节点存放完整索引项，并通过链表连接，适合范围查询和排序。
- 所有叶子节点在同一层，查询路径长度稳定。
- 磁盘 IO 友好，每次页读取可以带来多个 key。

相比哈希表，B+Tree 更适合范围查询、排序和前缀匹配。相比普通二叉树，B+Tree 高度更低，磁盘访问次数更少。

### 联合索引和最左匹配

联合索引遵循最左匹配原则。比如索引 `(a, b, c)`，可以支持：

- `where a = ?`
- `where a = ? and b = ?`
- `where a = ? and b = ? and c = ?`
- `where a = ? and b > ?`，但 `b` 之后的 `c` 很难继续用于精确定位。

常见索引失效或利用不充分：

- 左模糊匹配：`like '%abc'`。
- 对索引列做函数计算：`where date(create_time) = ...`。
- 对索引列做表达式计算：`where age + 1 = 18`。
- 隐式类型转换：字符串列用数字比较，可能导致索引失效。
- 不满足联合索引最左前缀。

联合索引字段顺序通常要综合考虑：

- 等值查询字段优先。
- 区分度高的字段靠前。
- 范围查询字段放在后面。
- 尽量让索引覆盖查询，减少回表。

### 如何优化索引

常见策略：

- 为高频查询条件、连接条件、排序字段建立合适索引。
- 使用联合索引覆盖多个查询条件。
- 使用覆盖索引减少回表。
- 对长字符串使用前缀索引，但要评估选择性。
- 主键尽量短、稳定、递增，避免随机主键导致页分裂和写放大。
- 避免在索引列上使用函数、表达式和不必要的隐式类型转换。
- 删除长期不用或重复的索引。

### EXPLAIN 常见 type

`EXPLAIN` 中 `type` 可以粗略判断访问方式，常见从差到好：

- `ALL`：全表扫描。
- `index`：全索引扫描。
- `range`：索引范围扫描。
- `ref`：非唯一索引等值匹配。
- `eq_ref`：连接中使用唯一索引或主键匹配，每次最多一行。
- `const`：通过主键或唯一索引定位到常量级结果。
- `system`：表只有一行的特殊情况。

一般 `ALL` 最需要警惕，但不能机械地认为 `range` 一定不好。小表全表扫描有时比走索引更快，最终要结合行数、过滤率、回表成本和执行耗时判断。

## 四、事务与 MVCC

### ACID

事务的 ACID：

- 原子性 Atomicity：事务内操作要么全部成功，要么全部失败。InnoDB 主要依赖 undo log 回滚。
- 一致性 Consistency：事务执行前后数据库从一个一致状态转到另一个一致状态。
- 隔离性 Isolation：并发事务之间互不干扰，依赖锁和 MVCC。
- 持久性 Durability：事务提交后即使宕机也能恢复，依赖 redo log 和刷盘策略。

可以这样理解：A、I、D 是实现一致性的手段，C 是事务最终目标。

### 并发事务问题

- 脏读：读到其他事务未提交的数据，之后对方回滚。
- 不可重复读：同一事务内两次读同一行，结果不同，因为其他事务提交了修改。
- 幻读：同一事务内两次范围查询，出现了新增或删除的记录。

解决手段包括事务隔离级别、MVCC、锁、间隙锁和临键锁。

### 事务隔离级别

MySQL/InnoDB 常见隔离级别：

- 读未提交 Read Uncommitted：可能读到未提交数据，会发生脏读。
- 读提交 Read Committed：每条一致性读语句生成新的 Read View，解决脏读。
- 可重复读 Repeatable Read：事务第一次一致性读时生成 Read View，事务内复用，解决不可重复读。InnoDB 默认隔离级别是 RR。
- 串行化 Serializable：读写都更严格地加锁，隔离最强，并发性能最低。

InnoDB 在 RR 下通过 MVCC 解决快照读的不可重复读，并通过 next-key lock 在当前读场景下尽量避免幻读。不要简单说“RR 绝对解决所有幻读”，要区分快照读和当前读。

### update 原子吗

单条 `UPDATE` 在 InnoDB 中是原子的。执行时会加锁，修改会写 undo log 和 redo log；成功则整体提交，失败则可以回滚。

但多个语句组成的业务操作是否原子，取决于是否放在同一个事务中。

### undo log 和 Read View

InnoDB 每行记录有 `trx_id` 和 `roll_ptr`。当行被更新时，旧版本会写入 undo log，并通过 `roll_ptr` 形成版本链。

Read View 可以理解为一致性读的可见性快照，里面记录当前活跃事务 ID 列表、最小活跃事务 ID、下一个将分配的事务 ID 等信息。

判断版本是否可见时，会结合行版本的 `trx_id` 和 Read View：

- 创建该版本的事务已经提交且在 Read View 可见范围内，则可见。
- 创建该版本的事务还活跃，或在 Read View 之后才开始，则不可见。
- 不可见时沿 undo 版本链向前找旧版本。

## 五、锁

### 锁类型和用途

全局锁会让整个数据库处于只读状态，典型用途是全库逻辑备份。常见命令是 `FLUSH TABLES WITH READ LOCK`，但 InnoDB 备份更常使用一致性快照工具，减少阻塞。

表级锁：

- 表锁：锁整张表，粒度大。
- 元数据锁 MDL：执行 CRUD 时会加 MDL 读锁，执行 DDL 时需要 MDL 写锁，防止表结构和读写并发冲突。
- 意向锁：表级锁，用于快速判断表中是否存在行级锁，避免逐行检查。

行级锁：

- 记录锁 Record Lock：锁住具体索引记录。
- 间隙锁 Gap Lock：锁住索引记录之间的间隙，防止插入。
- 临键锁 Next-Key Lock：记录锁 + 间隙锁，锁住左开右闭区间，常用于 RR 下防止幻读。

临键锁在特定条件下可能退化为记录锁或间隙锁。比如唯一索引等值查询命中具体记录时，通常可以退化为记录锁；查询不存在记录时可能锁住间隙。

### 当前读和快照读

快照读读取的是 MVCC 可见版本，不加行锁，常见普通 `select`。

当前读读取最新版本，并可能加锁，例如：

```sql
select ... for update;
select ... lock in share mode;
update ...;
delete ...;
insert ...;
```

很多幻读和间隙锁问题都发生在当前读语义下。回答事务问题时先区分快照读和当前读，会更准确。

## 六、日志

### 日志类型

- redo log：InnoDB 物理日志，记录页的物理修改，用于崩溃恢复，保证持久性。
- undo log：记录旧版本，用于事务回滚和 MVCC。
- binlog：Server 层逻辑日志，记录所有变更，用于主从复制和数据恢复。
- relay log：从库拉取主库 binlog 后写入本地的中继日志。
- 慢查询日志：记录执行时间超过阈值的 SQL，用于性能分析。

### undo log 会写磁盘吗

会。undo log 本身存放在 undo tablespace 或系统表空间中，修改时也会经过 Buffer Pool 中的 undo 页，并按刷脏机制持久化到磁盘。

不要把“先写到 Buffer Pool”误解为“不落盘”。事务回滚和 MVCC 依赖 undo log 的持久化管理。

### 为什么有 undo log 还要 redo log

两者解决的问题不同：

- undo log 记录修改前的旧版本，用于回滚和 MVCC。
- redo log 记录页修改后的物理变化，用于崩溃恢复。

如果只有 undo log，可以回滚未提交事务，但无法高效恢复已提交但还没刷到数据页的修改。redo log 让 InnoDB 可以先写日志再延迟刷数据页。

### redo log 如何保证持久性

redo log 使用 WAL，也就是 Write-Ahead Logging：修改数据页前，先保证对应日志按规则写入 redo log。

执行修改时，数据页先在 Buffer Pool 中变脏，同时生成 redo log。事务提交时，根据 `innodb_flush_log_at_trx_commit` 策略决定是否把 redo log 从 log buffer 写入并 fsync 到磁盘。

常见配置：

- `1`：每次提交都写入并刷盘，持久性最好，性能成本最高。
- `2`：每次提交写入文件系统缓存，通常每秒刷盘。
- `0`：每秒写入和刷盘，性能更高但宕机丢失风险更大。

### 能不能只用 binlog 不用 redo log

不行。

binlog 是 Server 层逻辑日志，面向复制和逻辑恢复；redo log 是 InnoDB 层物理日志，面向崩溃恢复。

redo log 能记录哪些数据页修改还没有真正刷盘，崩溃后 InnoDB 可以重放 redo 恢复到提交状态。binlog 无法替代这种页级崩溃恢复能力。

### redo log 和 binlog 的两阶段提交

为了保证 redo log 和 binlog 一致，MySQL 使用两阶段提交：

1. InnoDB 写 redo log，状态为 prepare。
2. Server 层写 binlog。
3. InnoDB 提交事务，把 redo log 标记为 commit。

崩溃恢复时，可以根据 redo prepare 状态和 binlog 是否完整来判断事务应提交还是回滚。两阶段提交的成本是额外 IO 和协调开销，但它保证了事务日志和复制日志的一致性。

## 七、调优与工程问题

### 主从延迟

主从延迟常见原因：

- 主库写入压力大，从库 SQL 线程回放跟不上。
- 大事务或大批量 DDL/DML 阻塞复制。
- 从库硬件性能不足。
- 网络延迟。
- 从库执行了慢查询或锁等待。

常见处理：

- 关键读强制走主库。
- 拆分大事务，减少单次复制压力。
- 优化慢 SQL 和索引。
- 使用并行复制。
- 监控 `Seconds_Behind_Master` 或新版本复制延迟指标。

### 分库分表

分库分表用于降低单库、单表的数据量和访问压力。

常见目标：

- 降低单表数据量，减少索引高度和扫描成本。
- 分散连接数和写入压力。
- 提升扩展能力。

代价：

- 跨库 join、排序、分页复杂。
- 分布式事务成本高。
- 全局唯一 ID、路由规则、扩容迁移都需要额外设计。

面试回答要说明：分库分表不是第一选择，通常在索引优化、SQL 优化、缓存、读写分离、硬件扩容之后再考虑。

### 慢 SQL 和索引优化流程

常见流程：

1. 打开慢查询日志，定位慢 SQL。
2. 使用 `EXPLAIN` 查看访问类型、索引、扫描行数、过滤率、回表和排序情况。
3. 检查 where、join、order by、group by 是否能利用索引。
4. 设计联合索引或覆盖索引。
5. 避免索引失效写法。
6. 对大 SQL 做分页、拆分或缓存。
7. 上线后继续观察执行时间、行数和锁等待。

### 表结构变更的数据可用性

大表 DDL 可能造成长时间锁表或复制延迟。常见方案：

- 使用在线 DDL 能力。
- 使用影子表：创建新表，增量同步数据，校验后切换。
- 使用 pt-online-schema-change 或 gh-ost 等工具。
- 避免业务高峰执行大变更。

影子表的核心思想是：不直接在原表上做高风险变更，而是构建新结构并逐步迁移，最后短时间切换。

## 八、面试速答

- 三大范式：1NF 原子性，2NF 消除部分依赖，3NF 消除传递依赖。
- InnoDB 支持事务、行锁、聚簇索引和崩溃恢复；MyISAM 不支持事务，主要表锁。
- MySQL 8.0 已移除 Query Cache，不要把它当作现代 SELECT 默认流程。
- InnoDB 页默认 16KB，逻辑结构是表空间、段、区、页、行。
- 聚簇索引叶子节点存整行数据，二级索引叶子节点存主键值。
- B+Tree 高度低、叶子有序链表，适合范围查询。
- 联合索引遵循最左匹配，函数、表达式、隐式转换、左模糊可能导致索引失效。
- ACID 中 undo 保证原子性，redo 保证持久性，锁和 MVCC 保证隔离性。
- InnoDB RR 下通过 MVCC 和 next-key lock 降低幻读风险，但要区分快照读和当前读。
- redo log 用于崩溃恢复，binlog 用于复制和逻辑恢复，二者不能互相替代。
- redo 和 binlog 通过两阶段提交保证一致。
- 慢 SQL 优化从慢查询日志、EXPLAIN、索引设计和 SQL 改写开始。
