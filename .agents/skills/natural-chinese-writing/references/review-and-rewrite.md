# 自然中文审查与改写

## 判断顺序

先回答三个问题：

1. 这句话提供了什么事实、推理、态度或必要节奏？
2. 删除格式、术语或修辞以后，信息是否变化？
3. 它是否符合全文已有的作者声音，还是可以无损迁移到任何主题？

如果一段话几乎不提供新信息，又呈现出可批量复制的结构，删除或替换它。不要看到列表、表格、三段式、英文、Emoji 或总结就自动判错；判断依据是必要性、信息增益和上下文。默认在原文上局部修改，不主动压缩篇幅或重组全文。

## 优先处理的信号

### 正面讲清机制

逐句查找否定表达，覆盖“并不意味着”“不能”“并非”“不代表”“不是……而是……”及语义相近的句式。仅当反例非常常见、具有代表性且显著辅助当前解释时保留，并紧接具体推演。其余写成对象、操作、条件和结果；缺少信息增益的句子直接删除。

技术条件通过明确模型和适用范围表达。数学公式、代码、原文引文保持其语义。关键词搜索用来定位候选，逐句语义审读决定如何处理。

### 强行凑成三项

检查三项并列、三个形容词、三个阶段和“从 A、B 到 C”式收束。若各项不是独立信息，或第三项只是为显得全面而补入，合并近义项、删除空泛项，或改成自然的一两句话。真正有用的三项应保留。

不要把空泛的三项换成另一组三项。表格、列表和编号若不能帮助比较、查找或执行，也应简化。

### 重复预告、路标和总结

删除已被标题说明的开场句、逐节重复的“第一个/接下来/这就进入”，以及与正文同义的结尾复述。长文可以保留真正帮助定位的路标。

### 把普通事实强行升华为意义、遗产或趋势

检查具体事实后是否突然添加意义、象征、遗产或行业趋势。常见线索包括“标志着、见证了、体现/证明了、凸显其重要性、反映更广泛的、象征着、关键转折点、不断演变的格局、不可磨灭的印记、深深植根于、奠定基础、塑造着”，以及用“作为/充当”包装普通对象。

这些词不是禁词。若前文没有事实和推理支撑宏观判断，就删除整句或改成具体影响；不要在结尾凭空添加启示、未来影响或普遍价值。

## 次要信号

以下现象不能单独作为改写理由。只有它们反复出现、明显干扰阅读，而且修改不会损失作者风格时才处理。

### 界面式符号和机械强调

删除用来指挥注意力而非表达情绪的 Emoji、密集粗体、整齐分隔线和装饰性提示框。强调应来自内容与段落位置。

### 空泛、对称和可迁移句式

警惕排比口号、过度对称、同义反复，以及“更高效、更稳定、更智能”等缺少判断标准的形容。换成对象、条件、动作和结果；无法具体化又不承载作者态度时就删除。

## 改写方法

1. 提取不可损失项，标出论点之间的依赖和必要结构。
2. 保留原文篇幅和组织方式，对高置信度问题做局部修改；用户要求压缩或重组时才大范围合并。
3. 用具体对象和动作替换抽象标签，用适用条件约束经验判断。
4. 从原文推断句长、正式程度、技术密度和叙述距离，保留有辨识度且有作用的表达。
5. 检查改写稿有没有新增事实、改变立场、删除关键边界，或产生新的统一模板腔。
6. 逐句查找否定表达，对每处记录三个例外条件是否同时成立。符合条件的反例接上具体推演；其余改为正面说明或删除。
7. 通读改写结果，检查是否仍在假设读者误解、发出泛化提醒或重复限定；回到执行步骤、因果链与算例补足解释。复查无依据的升华和凑数三项。

## 诊断格式

先给一句总体判断，再列最严重的具体问题。每项包含：

- 原文片段或位置。
- 它为什么影响阅读或可信度。
- 应删除、合并、具体化、收窄还是保留。

不要机械覆盖所有信号。没有问题的项目不写。

## 从头写作

先确定读者需要获得的信息和作者真正持有的观点，再选择结构。不要先决定文章必须有若干原则、阶段或表格。初稿完成后按本文件重新审查；形式有明确作用就保留，否则简化。

## 改写示例与验收

以下示例均改为直接解释机制。检验重点是有效信息、适用条件和因果关系是否清楚。

| 原表达 | 正面写法 |
| --- | --- |
| 跨全部层共 2 MiB，这并不意味着运行时使用一个连续对象。 | 2 MiB 是全部层的载荷之和；各层可分别存储张量，通过块编号关联。 |
| 不能仅凭树能表示任意长度前缀就认为物理缓存能零成本共享。 | 树匹配出 9-token 前缀；按 4-token 完整块共享时，复用前 8 tokens，从第 9 个开始计算。 |
| 共享也不会使 Decode 免费。 | Decode 时，每个请求用自己的 Query 读取共享 KV，分别计算 Attention 输出。 |
| 最高命中率并不必然让最多用户更快完成。 | 同时记录复用 token 数、节省的重算时间和请求延迟，用端到端结果衡量淘汰策略的收益。 |
| 这里的软件层级不是硬件自动保持一致的 CPU Cache。 | 分级缓存由运行时维护数据位置、完整性和传输完成状态。 |
| 选择性写回减少流量，却可能产生复制压力，还需要额外统计和判断。 | 选择性写回根据前缀的复用次数决定保留对象；回收尚未建立下层副本的 GPU 块时，先完成复制再释放。 |
| 不能默认所有数据丢失都能无代价恢复。 | 历史缓存加载失败后，释放目标槽位，重新计算前缀。活跃请求按保存的输入和执行进度重建状态。 |

验收时逐项检查：事实和必要条件得到保留；动作与结果具体；新增实现细节有依据。示例中的恢复方案适用于已保存重建所需输入与执行进度的系统，实际文章按已核实的方案表述。
